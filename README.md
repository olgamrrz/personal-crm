# Личная CRM

Приложение, где я веду контакты людей, которых знаю лично. Подробнее - `specs/01-продуктовая-идея.md`.

Что умеет:

- вход по ссылке из письма, без пароля: человек вводит почту, получает письмо и входит. Первый вход и есть регистрация. Вход держится 30 дней с последнего захода, в шапке - почта и «Выйти»
- у каждого человека свои контакты, заметки и группы: чужих не видно ни на экране, ни прямым запросом к серверу
- список всех контактов и поиск по имени (регистр и «ё/е» не важны)
- добавление контакта: имя, кто это, откуда знакомы, телефон, почта
- карточка контакта с заметками: после разговора дописываю, о чём договорились
- удаление контакта вместе с его заметками: сначала приложение спрашивает подтверждение
- группы контактов (семья, друзья, теннис - какие захочу): страница «Группы» на главной, там группу можно создать, переименовать и удалить; при удалении группы контакты остаются, только выходят из неё. Контакт может быть в нескольких группах сразу
- группу назначаю в карточке контакта (строка «Группы», сохраняется сразу) и при создании контакта; новую группу можно создать прямо в этом поле
- на главной под поиском - фильтр по группе (работает вместе с поиском, выбранная группа видна в адресе страницы), а в каждой строке списка - метки групп контакта

## Что нужно установить

- Docker Desktop (должен быть запущен)
- Node.js 20 или новее и pnpm
- OpenSpec - для работы над фичами (спеки в `openspec/`): `curl -fsSL https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/scripts/binary/install.sh | sh`

## Первый запуск

1. Скопировать шаблон настроек: `cp .env.example .env`
2. Заполнить в `.env` все значения (пароль - любой длинный случайный). Строки для входа и почты локально такие:

   | Строка | Значение |
   | --- | --- |
   | `BETTER_AUTH_SECRET` | случайный секрет, получить командой `openssl rand -base64 32` |
   | `BETTER_AUTH_URL` | `http://localhost:3000` |
   | `SMTP_HOST` | `127.0.0.1` |
   | `SMTP_PORT` | `1025` |
   | `SMTP_SECURE` | `false` |
   | `SMTP_USER`, `SMTP_PASSWORD` | оставить пустыми |
   | `MAIL_FROM` | `noreply@mail.crm.example.com` (локально письма никуда не уходят, адрес любой) |
   | `OWNER_EMAIL` | ваша почта: ей достанутся контакты, которые уже были в базе до входа, и тестовые данные |
3. Установить зависимости: `pnpm install`
4. Запустить базу: `docker compose up -d`
5. Создать таблицы: `pnpm db:migrate`
6. По желанию - заполнить базу тестовыми данными (1000 контактов): `pnpm db:seed`.
   Контакты достанутся пользователю с почтой `OWNER_EMAIL`. Если у него уже есть контакты, ничего не изменится.
7. Запустить приложение: `pnpm dev`
8. Открыть в браузере: http://localhost:3000 и войти (см. «Как войти локально» ниже)
9. Для e2e-тестов один раз скачать браузер, которым они пользуются (около 300 МБ): `pnpm exec playwright install chromium`

## Обычный запуск

```
docker compose up -d
pnpm dev
```

Приложение откроется на http://localhost:3000. Остановить - `Ctrl+C` в терминале.

Локально приложение, база и почтовая заглушка доступны только с этого компьютера, из сети их не видно.

### Как войти локально

Письма локально никуда не уходят: их ловит заглушка Mailpit, она запускается вместе с базой (`docker compose up -d`).

1. Открыть http://localhost:3000, ввести любую почту (можно выдуманную, например `anna@example.com`) и нажать «Получить ссылку»
2. Открыть http://localhost:8025 - это страница Mailpit со всеми «отправленными» письмами. Открыть письмо «Вход в Личную CRM» и нажать в нём «Войти»
3. Откроется главная. «Выйти» - в шапке справа

Чтобы увидеть, как это выглядит у другого человека: выйти и войти с другой почтой, например `boris@example.com`. Контактов Анны у него не будет.

## База данных

PostgreSQL работает в Docker. Настройки подключения лежат в файле `.env` - он не попадает в git. Рядом в Docker работает Mailpit - заглушка почты (см. «Как войти локально»).

Проверить, что база работает (в колонке STATUS у `db` должно быть `healthy`, а `mailpit` - запущен):

```
docker compose ps
```

Остановить базу (данные сохранятся):

```
docker compose down
```

Данные хранятся в Docker-томе `personal-crm_postgres_data`. Команда `docker compose down -v` удалит их безвозвратно.

## Тесты

Перед тестами должны быть запущены база и Mailpit в Docker (`docker compose up -d`): тесты работают на настоящей базе и читают настоящие письма из заглушки, без подмен.

```
pnpm test
```

Тесты не трогают рабочую базу. Они сами создают рядом отдельную базу с тем же именем и окончанием `_test` (например, `crm_test`), применяют к ней миграции и перед каждым тестом очищают её таблицы. Если имя базы не кончается на `_test`, тесты не запустятся. Отдельных настроек в `.env` не нужно.

### e2e-тесты

e2e-тесты проходят главный сценарий из `specs/01-продуктовая-идея.md` в настоящем браузере, как человек: открыть список, добавить контакт, найти его по имени, дописать заметку, открыть тот же адрес во втором браузере. Лежат в папке `e2e/`.

```
pnpm test:e2e
```

- нужны запущенные база и Mailpit в Docker и скачанный браузер (шаг 9 первого запуска)
- каждый тест сначала входит по ссылке из письма, как человек; для этого письмо читается со страницы Mailpit
- приложение собирается так же, как для сервера, и запускается на порту 3100, поэтому `pnpm dev` на 3000 можно не останавливать; сборка занимает около минуты
- у e2e своя база с окончанием `_e2e_test` (например, `crm_e2e_test`): тесты сами её создают и очищают перед каждым тестом, рабочие данные и базу обычных тестов не трогают
- если тест упал, в папке `playwright-report/` остаётся отчёт со скриншотом и записью каждого шага; открыть - `pnpm exec playwright show-report`

## Проверки в PR (CI)

В `main` изменения попадают только через PR, и только когда CI зелёный: так настроена защита ветки на GitHub. Напрямую в `main` не пушится, даже владельцу.

На каждый PR GitHub запускает `.github/workflows/ci.yml`: четыре проверки, их видно внизу страницы PR:

| Проверка | Что делает |
| --- | --- |
| Lint, format, types | `pnpm lint`, `pnpm format:check`, `pnpm typecheck` |
| Unit tests | `pnpm test` на настоящей базе Postgres и заглушке Mailpit |
| E2E tests | `pnpm test:e2e` в браузере на настоящей базе и заглушке Mailpit; если упали, отчёт со скриншотами лежит на странице запуска в Actions, блок Artifacts |
| Docker image | собирает образ по `Dockerfile`, никуда его не отправляет |

PR вливается сам (автовлитие): когда все четыре проверки зелёные, GitHub делает squash merge в `main`, и начинается выкатка. Если PR отстал от `main`, GitHub попросит его обновить: кнопка «Update branch» в PR.

Упала проверка формата - запустить `pnpm format`, закоммитить и запушить.

## Выкатка на сервер

Приложение работает на https://app.olgamrzvcrm.ru. Войти можно только по ссылке из письма; у каждого человека свои контакты.

Выкатка автоматическая: **каждый push в ветку `main` сам выкатывает новую версию** и на тест-стенд, и на прод. Это два независимых шага одного запуска: упала выкатка на стенд - прод всё равно выкатывается, и наоборот. Один и тот же скрипт `deploy/deploy.sh` и один `deploy/compose.yaml` работают на обоих, окружение - параметром: `deploy.sh prod SHA` или `deploy.sh staging SHA`. Ход выкатки виден на GitHub, вкладка Actions:

1. GitHub собирает образ приложения по `Dockerfile` с тегом - SHA коммита - и кладёт его в GHCR (один образ для стенда и прода)
2. Для каждого окружения копирует на сервер всю папку `deploy/` (стенд - в `/opt/crm/staging`, прод - в `/opt/crm/prod`) и запускает `deploy.sh`. Шаги для прода:
   - поднимает базу
   - снимает бэкап базы скриптом `backup.sh` в `/opt/crm/prod/backups`; в имени файла - версия, которая стояла до выкатки. Не получился бэкап - выкатка останавливается, ничего не меняется
   - применяет миграции разовым контейнером из нового образа; упали миграции - новая версия не запускается, работает прежняя
   - запускает новую версию
   - проверяет `/health`: должен ответить 200, иначе выкатка красная
   - оставляет на сервере текущий и предыдущий образы каждого окружения: образ у стенда и прода общий, поэтому выкатка на стенд не удаляет образ, к которому можно откатить прод
3. Проверяет снаружи https://app.olgamrzvcrm.ru/health

У стенда те же шаги, но без бэкапа: бэкапы снимаются только на проде. Снаружи проверяется, что адрес стенда закрыт паролем (ответ 401).

Красный крестик в Actions - выкатка упала. Сама она ничего не откатывает.

Что сейчас на сервере: Actions → Deploy → верхний запуск. На схеме под «Deploy to staging» и «Deploy to prod» ссылки на приложения, вверху - коммит, который выкачен. Список всех выкаток - блок «Deployments» справа на главной странице репозитория: `staging` и `production`.

### Тест-стенд

Адрес: https://test-app.olgamrzvcrm.ru. Закрыт паролем (логин и пароль браузер спросит при открытии; создаются на сервере, в git их нет). Это такая же сборка, как на проде, со своими данными:

| Что | Стенд | Прод |
| --- | --- | --- |
| Адрес | `test-app.olgamrzvcrm.ru` | `app.olgamrzvcrm.ru` |
| Папка на сервере, проект docker compose | `/opt/crm/staging`, `staging` | `/opt/crm/prod`, `prod` |
| Свои настройки и ключи | `/opt/crm/staging/.env`, права 600 | `/opt/crm/prod/.env`, права 600 |
| База | Docker-том `staging_postgres_data` | Docker-том `prod_postgres_data` |
| Порт на сервере (только с самого сервера) | 3001 | 3000 |
| Лимит памяти контейнеров | приложение 384 МБ, база 256 МБ | нет |
| Бэкапы | нет, данные - копия прода | есть |
| nginx | `/etc/nginx/sites-available/test-app.olgamrzvcrm.ru.conf` | блок `app.olgamrzvcrm.ru` |

- Письмо со ссылкой входа уходит настоящему адресату, ссылка в нём ведёт на адрес того окружения, где запросили вход: адрес берётся из `BETTER_AUTH_URL` в `.env` окружения
- Кука входа привязана только к адресу своего окружения (без общего домена `olgamrzvcrm.ru`): вход на стенде не работает на проде и наоборот. Проверить: в браузере DevTools → Application → Cookies, у куки `better-auth.session_token` колонка Domain - `test-app.olgamrzvcrm.ru`, без точки впереди
- Два выката на один стенд одновременно не идут: в GitHub второй ждёт первого, а если запустить `deploy.sh` на сервере вручную во время другой выкатки - он остановится с ошибкой `another deploy or restore is running in staging`
- Сертификат для стенда выпущен certbot отдельно, продлевается сам вместе с остальными

#### Обновить данные стенда копией прода

Данные стенда - копия базы прода из последнего бэкапа. Испортились - пересоздать из свежего бэкапа (если нужна свежее, сначала снять бэкап прода: `ssh crm bash /opt/crm/prod/backup.sh`):

```
ssh -t crm bash /opt/crm/staging/restore.sh staging
```

Без файла скрипт берёт самый свежий бэкап из `/opt/crm/prod/backups`, пишет, какой именно, показывает, какую базу заменит, и ждёт `yes`. Дальше останавливает приложение стенда, заменяет базу, применяет миграции (бэкап прода может быть старше версии стенда) и запускает приложение. Версия приложения стенда не меняется. Прод и его база не затрагиваются.

В базе стенда настоящие контакты прода: письма со входом отправляются настоящим адресатам, поэтому на стенде входите под своей почтой.

### Вход и почта на сервере

Письма со ссылкой на сервере уходят настоящим адресатам через сервис Resend. Одна и та же сборка приложения работает и локально, и на сервере: куда слать письма, решают строки в `/opt/crm/prod/.env` (шаблон - `deploy/.env.example`). Если какой-то строки нет, выкатка остановится ещё до бэкапа и скажет, какой. У тест-стенда свой `/opt/crm/staging/.env` с теми же строками, но свои значения: другой секрет, другой пароль базы, `BETTER_AUTH_URL=https://test-app.olgamrzvcrm.ru` и свой ключ почты Resend.

| Строка | Значение на сервере |
| --- | --- |
| `BETTER_AUTH_SECRET` | случайный секрет, получить командой `openssl rand -base64 32`; не менять без нужды: у всех сразу закончится вход |
| `BETTER_AUTH_URL` | `https://app.olgamrzvcrm.ru` |
| `SMTP_HOST` | `smtp.resend.com` |
| `SMTP_PORT` | `465` |
| `SMTP_SECURE` | `true` |
| `SMTP_USER` | `resend` |
| `SMTP_PASSWORD` | ключ API из Resend |
| `MAIL_FROM` | адрес отправителя на подтверждённом домене, например `noreply@mail.crm.<домен>` |
| `OWNER_EMAIL` | почта владельца: ей достанутся контакты, которые были в базе до появления входа |

Перед первой выкаткой входа в Resend нужно добавить домен отправки и прописать записи DNS (SPF и DKIM), которые он покажет, - иначе письма уйдут в спам или не дойдут. Пока Resend не показывает домен подтверждённым, никто не сможет войти, включая владельца.

После выкатки: войти на https://app.olgamrzvcrm.ru под почтой `OWNER_EMAIL`; числа контактов, заметок и групп должны совпасть с теми, что были до выкатки. Потом пусть войдёт второй человек: у него должен быть пустой список.

## Восстановление базы из бэкапа

Восстанавливаю только я, вручную, командой на сервере. Выкатка и сервер сами базу никогда не восстанавливают. Скрипт `restore.sh` берёт окружение первым параметром: `prod` - как описано ниже, `staging` - копия данных прода для тест-стенда (см. «Тест-стенд»).

### Бэкапы

Бэкапы снимает скрипт `deploy/backup.sh`, на сервере - `/opt/crm/prod/backup.sh`. Файлы лежат в `/opt/crm/prod/backups`, в имени - дата, время и версия приложения, которая стояла в этот момент:

| Файл | Кто снимает | Сколько хранится |
| --- | --- | --- |
| `2026-11-04_143012_SHA.dump` | каждая выкатка, перед миграциями | 30 последних |
| `2026-11-04_143012_SHA_manual.dump` | я вручную: `ssh crm bash /opt/crm/prod/backup.sh` | не удаляется автоматически |
| `2026-11-04_143012_SHA_before-restore.dump` | restore, перед тем как удалить базу | не удаляется автоматически |

С версией из имени данные из бэкапа точно работают. Бэкапы лежат на том же сервере: пропадёт сервер - пропадут и они.

### Как восстановить

1. Найти нужный бэкап: `ssh crm ls -l /opt/crm/prod/backups`
2. Запустить restore с полным путём к файлу:

   ```
   ssh -t crm bash /opt/crm/prod/restore.sh prod /opt/crm/prod/backups/2026-11-04_143012_SHA.dump
   ```

3. Скрипт проверит, что файл - настоящий бэкап, и покажет: какой файл, когда снят, при какой версии, какую базу заменит и какая версия приложения сейчас стоит. Если версия бэкапа другая - предупредит
4. Чтобы продолжить, ввести `yes`. Любой другой ответ - выход, ничего не меняется
5. Дальше скрипт сам:
   - снимает копию текущей базы: `/opt/crm/prod/backups/ДАТА_ВРЕМЯ_SHA_before-restore.dump`
   - останавливает приложение
   - удаляет базу, создаёт её заново пустой и загружает в неё бэкап
   - запускает ту же версию приложения, что стояла, и проверяет `/health`
6. В конце пишет `Restored database ...` и где лежит копия данных до восстановления

Версию приложения restore не меняет. Пока restore ждёт `yes` и работает, выкатка не идёт: она падает с ошибкой `another deploy or restore is running in prod`. После восстановления её можно перезапустить: Actions → Deploy → упавший запуск → «Re-run all jobs».

### Вернуть и версию, и данные

Например, новая версия испортила данные. Бэкап, который она сняла перед своими миграциями, назван версией до неё.

1. Откатить версию на SHA из имени бэкапа: `ssh crm bash /opt/crm/prod/deploy.sh prod SHA`
2. Восстановить этот бэкап, как выше

### Откат выкатки, в которой появился вход

Для этой выкатки порядок обратный общему. Старая версия без входа, запущенная на новой базе, показала бы любому посетителю все контакты, потому что в новой базе у каждого контакта есть владелец, а старая версия про это не знает. Поэтому:

1. Сначала восстановить базу из бэкапа, который снят этой выкаткой (самый свежий `..._SHA.dump` перед ней): новая версия на старой базе не откроется, но и данные никому не покажет
2. Потом выкатить прошлую версию: `ssh crm bash /opt/crm/prod/deploy.sh prod SHA`, где `SHA` - версия из имени бэкапа

Всё, что люди успели добавить после выкатки, при таком откате пропадёт: оно лежит только в новой базе.

### Если что-то пошло не так

- Restore остановился до удаления базы (не тот файл, не получилась копия, ответ не `yes`) - ничего не изменилось, приложение работает
- Restore упал при загрузке бэкапа - приложение остановлено, база может быть пустой. Скрипт пишет команду, которой вернуть прежние данные: тот же restore с файлом `_before-restore`
- База восстановлена, но приложение не отвечает на `/health` - смотреть логи: `ssh crm docker logs --tail 100 prod-app-1`. Сам скрипт ничего не откатывает
