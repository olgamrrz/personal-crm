# Design

## Context

Зачем фича - в proposal.md, что именно должно работать - в `specs/keep-in-touch/spec.md`. Как выглядят экраны - в макете: https://claude.ai/artifact/5Nm3xiPA8egrMB9TzQvrqr (список экранов - в proposal.md, раздел «Макеты»; при расхождении верны требования).

Что есть сейчас:

- Таблицы `contacts` и `notes` (`src/db/schema.ts`). Заметки только добавляются: правки и удаления нет, при удалении контакта его заметки удаляются вместе с ним
- Карточку контакта нельзя редактировать: только создать и удалить. Карточка - серверный компонент `src/app/contacts/[id]/page.tsx`, поля показаны строками `DetailRow`
- Главная `src/app/page.tsx`: один асинхронный компонент `Contacts` внутри `Suspense` рисует поиск и список. Поиск при вводе меняет `?q=`, компонент перерисовывается
- Строки списка (`ContactRows`) - клиентский компонент: сервер отдаёт компактный массив, строка целиком - ссылка на карточку
- Включены Cache Components (`cacheComponents: true`): текущее время в JS (`Date.now()`) требует отдельной обработки, а запросы к базе и так выполняются на каждый запрос
- Часовой пояс нигде не задан: в Docker-образе сервер работает по UTC
- Автотестов в проекте нет, тестовой библиотеки нет
- shadcn/ui: из компонентов есть button, card, input, label, textarea, alert-dialog. Select нет, но его основа `@base-ui/react` уже в зависимостях

## Goals / Non-Goals

**Goals:**

- Один источник правды для «сегодня» и календарной арифметики, чтобы граница «в день срока ещё нет, на следующий день - да» не зависела от часового пояса сервера
- Одно правило «последнее общение» для блока и для карточки: оно задаётся в одном месте и не может разойтись
- Миграция только добавляет поля: старая версия приложения работает с новой базой, откат образа безопасен
- Главная не «прыгает»: блок и список появляются вместе

**Non-Goals:**

- Редактирование остальных полей контакта
- История нажатий «Пообщались» и их отмена
- Исправление показа времени заметок по UTC (см. Risks)
- Автотесты и тестовая библиотека: новую библиотеку нужно сначала обсудить с владельцем

## Decisions

### 1. Модель данных: три поля в `contacts`

- `contact_frequency` - `text`, может быть пустым; CHECK разрешает только `week`, `month`, `quarter`, `year`. Пусто = «не задано»
- `contact_frequency_set_at` - `timestamptz`, может быть пустым: когда частоту выбрали или изменили в последний раз. Сбросили на «не задано» - оба поля пустые
- `last_contacted_at` - `timestamptz`, может быть пустым: когда последний раз нажали «Пообщались». Сброс частоты это поле не трогает

«Последнее общение» не храним, а считаем: `greatest(max(notes.created_at), last_contacted_at)`, а если оба пустые - `contact_frequency_set_at`. `greatest` в Postgres пропускает пустые значения.

Альтернативы:

- Postgres enum вместо `text` + CHECK - значения enum трудно убрать или переименовать позже; CHECK меняется обычной миграцией
- Хранить срок в днях (7/30/90/365) - теряется календарный месяц из требований (15 марта → 15 апреля)
- «Пообщались» создаёт заметку - владелец отказался: в заметках копились бы одинаковые записи, а удалить заметку нельзя
- Отдельная таблица отметок с историей - истории нет в требованиях; одно поле проще
- Хранить «последнее общение» целиком и обновлять при каждой заметке - лишнее состояние, которое может разойтись с заметками

### 2. Просрочку считает Postgres одним запросом

Выражение «последнее общение» - один SQL-фрагмент в `src/lib/contacts.ts`; его используют и блок, и карточка.

Новая функция, например `listOverdueContacts()`:

- берёт контакты с заданной частотой и самую позднюю заметку каждого (`left join` + `max`)
- последнее общение - по правилу из раздела 1
- день последнего общения и «сегодня» - даты по Москве: `(ts at time zone 'Europe/Moscow')::date`, «сегодня» - от `now()`
- срок = день последнего общения + `interval` по частоте (`7 days`, `1 month`, `3 months`, `1 year`). Postgres сам считает календарный месяц и прижимает к концу месяца: `2026-01-31 + 1 month = 2026-02-28`
- просрочка = сегодня − срок, в днях; в выдачу - только больше нуля
- порядок: просрочка по убыванию, затем имя с той же русской сортировкой, что в списке (`collate "ru-RU-x-icu"`), затем `id`
- возвращает компактные строки: `id`, `name`, частота, дни просрочки

Для карточки - функция, например `getLastContact(contactId)`: возвращает день последнего общения по Москве (или пусто, если общения не было) и признак «сегодня», посчитанный в базе. Поэтому «сегодня» в карточке и в блоке определяется одинаково, без `Date.now()`.

Почему не в JS: «сегодня» через `Date.now()` при Cache Components потребовало бы `connection()`, а календарная арифметика с часовым поясом без библиотеки дат легко ошибается. У базы одни часы, и она уже умеет календарные интервалы.

Часовой пояс - одна константа в коде (`Europe/Moscow`), а не переменная окружения: он один на всё приложение, менять его - продуктовое решение.

### 3. Выбор частоты в карточке

- Компонент Select из shadcn/ui добавляется командой shadcn в `src/components/ui/select.tsx`. Это код в репозитории поверх уже установленной `@base-ui/react`, новой библиотеки нет
- Новый клиентский компонент, например `ContactFrequencySelect`: при выборе сразу вызывает серверное действие, показывает новое значение сразу (`useOptimistic`), при ошибке возвращает прежнее и показывает сообщение под списком
- Место - новая строка «Как часто общаться» в списке полей карточки, после «Почта»
- Варианты и их подписи («раз в месяц») - один список в `src/lib/`, его используют и выбор, и блок на главной

Альтернатива - обычный `<select>` браузера: проще, но выглядит иначе, чем остальной интерфейс shadcn/ui.

### 4. Серверное действие `setContactFrequency`

В `src/app/actions.ts`, рядом с остальными:

- проверяет `contactId` так же, как `addNote` и `deleteContact`, и значение - только из разрешённого списка или «не задано»
- обновляет частоту и `contact_frequency_set_at = now()` только если значение действительно поменялось (`is distinct from`): повторный выбор того же варианта не сбивает отсчёт у контакта без общения
- «не задано» - частота и `contact_frequency_set_at` в `null`; `last_contacted_at` не трогается
- контакт не найден - ошибка «Контакт не найден», как в других действиях
- после сохранения - `revalidatePath("/")` и `refresh()`, чтобы главная и карточка были свежими

### 5. Серверное действие `markContacted`

Одно действие для кнопки «Пообщались» и в блоке, и в карточке:

- проверяет `contactId` так же, как остальные действия
- `last_contacted_at = now()`; заметку не создаёт
- частоту не проверяет: без частоты кнопки нет, а лишняя отметка ничего не ломает
- контакт не найден - ошибка «Контакт не найден»
- после сохранения - `revalidatePath("/")` и `refresh()`
- переход на другую страницу не делает: пользователь остаётся там, где нажал

### 6. `addNote` тоже обновляет главную

Сейчас `addNote` вызывает только `refresh()`. Добавляем `revalidatePath("/")`: новая заметка убирает контакт из блока, и при возврате на главную блок должен быть уже верным. `deleteContact` уже вызывает `revalidatePath("/")`.

### 7. Блок на главной

- Данные блока грузятся в том же компоненте `Contacts`, параллельно со списком (`Promise.all`). Блок и список появляются вместе под одной заглушкой загрузки, поле поиска не сдвигается
- Блок стоит над поиском. Поиск блок не фильтрует: запрос просрочки не принимает `q`
- Запрос просрочки выполняется и при каждом поиске - он лёгкий (только контакты с частотой)
- Строки блока - новый клиентский компонент по образцу `ContactRows`. В отличие от него, строка - не одна ссылка: ссылка на карточку (аватар, имя, частота, «просрочено на N дней» через `pluralize`) и рядом отдельная кнопка «Пообщались». Кнопка внутри ссылки - недопустимая разметка, и нажатие на неё открывало бы карточку
- Нажали «Пообщались» - строка сразу скрывается (`useOptimistic`), число в заголовке уменьшается; последняя строка - скрывается весь блок. Ошибка - строка возвращается, в ней сообщение
- Раскладка как в макете: на компьютере частота под именем, просрочка и кнопка справа; на телефоне частота и просрочка под именем, кнопка справа, высота кнопок и строк не меньше 44 px
- Просроченных нет - блок не рисуется
- Цвета, отступы, шрифты - только дизайн-токены

Альтернатива - отдельный `Suspense` для блока: он появлялся бы позже списка и сдвигал поиск вниз.

### 8. «Последнее общение» в карточке

- Новая строка после «Как часто общаться», только когда частота задана
- Текст: «сегодня» - если база вернула признак «сегодня»; иначе дата без времени в московском поясе («19 сентября 2026 г.»); общения не было - «ещё не общались»
- Рядом кнопка «Пообщались» - клиентский компонент: вызывает `markContacted`, на время запроса неактивна; при ошибке - сообщение под кнопкой. После успеха карточка обновляется через `refresh()`, и в строке появляется «сегодня»
- Видимость строки зависит от частоты на странице: сбросили частоту на «не задано» - строка и кнопка пропадают сразу, вместе с новым значением выбора

## Risks / Trade-offs

- [Время заметок на сервере показывается по UTC, а блок и «Последнее общение» считают дни по Москве] → около полуночи дата у заметки и отсчёт в блоке могут расходиться на день. Исправить отдельной правкой: показывать время заметок по Москве
- [«Пообщались» нельзя отменить] → принимаем: ошибочное нажатие только сдвигает срок; контакт вернётся в блок через период
- [Отметки не оставляют следа в заметках] → решение владельца; в карточке видна только дата последнего общения
- [У контакта без общения отсчёт можно сбросить, поменяв частоту туда-обратно] → принимаем: так работает решение «считать от дня, когда задали»
- [Много просроченных - длинный блок над списком] → принимаем: в блоке все без ограничения; если станет мешать - отдельное решение владельца
- [На телефоне в строке блока тесно: имя, частота, просрочка и кнопка] → частота и просрочка под именем, как в макете; длинные имена обрезаются многоточием
- [Сгенерированный Select может не совпасть с установленной версией `@base-ui/react`] → после генерации проверить `pnpm lint` и `pnpm build`
- [Нет автотестов на расчёт сроков] → проверить граничные случаи запросом на локальной базе внутри транзакции с откатом, чтобы не оставить следов в данных

## Migration Plan

1. `pnpm db:generate` создаёт `drizzle/0001_*.sql`: три `ALTER TABLE contacts ADD COLUMN` и CHECK. Существующие строки получают пустые значения - «не задано», отметок нет
2. Выкатка обычная: merge → образ → миграции разовым контейнером → новый образ → smoke `/health`
3. Откат - вручную, запускает владелец: предыдущий образ. Новые поля остаются в базе, старый код их не читает. Удалять поля не нужно
