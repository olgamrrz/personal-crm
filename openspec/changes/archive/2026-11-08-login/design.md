# Design

## Context

Зачем фича - в proposal.md, что именно должно работать - в `specs/user-login`, `specs/data-ownership` и дельте `specs/contact-groups`.

Что есть сейчас:

- Пользователей нет. Таблицы `contacts`, `notes`, `groups`, `contact_groups` (`src/db/schema.ts`). Уникальный индекс названий групп - по всей базе
- Чтение и запись - функции в `src/lib/contacts.ts` и `src/lib/groups.ts` (`server-only`), их вызывают страницы и серверные действия `src/app/actions.ts`. Функции ничего не знают о запросе - поэтому их легко проверять в Vitest на настоящей базе
- Включены Cache Components: всё, что читает запрос (`headers()`, cookie) или базу, - только внутри `Suspense`
- Next.js 16: `middleware` теперь называется `proxy`. Документация Next.js (`node_modules/next/dist/docs/01-app/02-guides/authentication.md`) советует: proxy - только быстрая проверка cookie, а настоящая проверка входа - рядом с данными
- Тесты: Vitest на базе `<имя>_test`, Playwright на базе `<имя>_e2e_test`, приложение для e2e собирается как в образе (`NODE_ENV=production`). Обе базы очищаются целиком перед каждым тестом
- Миграции: в образе - `scripts/migrate.mts` (одно соединение, мигратор Drizzle), локально - `drizzle-kit migrate`, в тестах - `test/database-setup.mts`
- Скрипт демо-данных копирует в образ `src/db/schema.ts` без остального `src/`: схема не может импортировать из `src/`
- В логах нет персональных данных (`src/lib/log-redaction.ts`)
- Почтовой заглушки в `compose.yaml` и CI пока нет
- Better Auth 1.7.18 (последняя на 2026-11-07), его CLI теперь пакет `auth`. Nodemailer 10.3.1. Проверено по исходникам Better Auth: ссылка по умолчанию живёт 5 минут; одноразовость встроена; запись ссылки хранит почту в JSON; встроенный лимит частоты работает по IP и только в production

## Goals / Non-Goals

**Goals:**

- Граница доступа - функции данных: каждая получает `ownerId` и сама фильтрует по нему. Страница или действие не может забыть проверку, потому что без `ownerId` функцию не вызвать
- Миграция переносит данные владельцу атомарно: или всё, или ничего, и выкатка останавливается
- Письма везде идут одним кодом, разница - только в настройках
- Всё проверяется без моков: Vitest и Playwright шлют письма в настоящий Mailpit и читают их оттуда

**Non-Goals:**

- Клиентская библиотека Better Auth (`better-auth/react`): форма входа - серверное действие, выход - тоже
- Защита от сканеров писем, которые открывают ссылки сами (см. риски)
- Хранилище лимитов в Redis и другие новые сервисы

## Decisions

### 1. Better Auth: настройка

`src/lib/auth.ts` (`server-only`):

- Адаптер Drizzle с существующим `db`, `provider: "pg"`, `usePlural: true` - таблицы `users`, `sessions`, `accounts`, `verifications`, как принято в проекте
- Плагин `magicLink`: `expiresIn: 900` (15 минут), `storeToken: "hashed"` - в базе только хеш ссылки, утечка базы не даёт рабочих ссылок. `sendMagicLink` вызывает отправку письма (раздел 4)
- `session.expiresIn` - 30 дней, `session.updateAge` - 1 час: срок сдвигается не чаще раза в час, отсюда «точность до часа»
- `disabledPaths: ["/sign-in/magic-link"]`: запросить ссылку по HTTP напрямую нельзя (404), только через наше серверное действие с проверкой почты и лимитом. Вызов `auth.api.signInMagicLink` с сервера при этом работает - он не проходит через HTTP-роутер
- `rateLimit.customRules["/magic-link/verify"] = false`: встроенный лимит по IP (5 переходов в минуту) за nginx без настройки IP превращается в общий на всех, а e2e входят много раз подряд. Подбирать ссылку бессмысленно: токен - 32 случайных символа. Лимит писем - наш, по почте (раздел 3)
- `telemetry: { enabled: false }`: ничего не уходит наружу
- Плагин `nextCookies()` последним: cookie ставятся из серверных действий
- Секрет и адрес приложения - из `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`
- Маршрут `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`): по нему работают ссылка из письма (`/api/auth/magic-link/verify`) и продление входа

Альтернативы: Auth.js - не из спеки; свой вход по токенам - больше кода и ошибок в безопасности.

### 2. Модель данных

- Таблицы Better Auth - в `src/db/schema.ts` рядом с остальными. Генерирует их `pnpm dlx auth@1.7.18 generate` под нашу настройку; результат проверяем глазами и переносим в схему. Имя пользователя (`name`) Better Auth требует - пишем пустую строку, имя не спрашиваем
- `contacts.owner_id` и `groups.owner_id` - `text not null`, ссылка на `users.id` **без** каскада: удаления пользователей в приложении нет, а случайное удаление пользователя в базе не должно унести его контакты. Индексы по `owner_id`
- Заметки и связи «контакт - группа» своего владельца не хранят: заметка принадлежит владельцу контакта, связь проверяется при записи (раздел 5)
- Уникальность названий групп: индекс `(owner_id, ключ названия)` вместо индекса по ключу названия
- `sign_in_emails` - отправленные письма для лимита: `id`, `email`, `sent_at`, индекс `(email, sent_at)`. Строки старше 10 минут удаляются при каждом запросе ссылки: почта хранится не дольше 10 минут

Альтернатива: `owner_id` в `contact_groups` и составные внешние ключи - база сама не даст связать чужие записи. Отказались: запросы и так обязаны фильтровать по владельцу, это закрыто тестами, а миграция и код станут заметно сложнее.

### 3. Запрос ссылки: проверка, лимит, гашение старых

Серверное действие `requestSignInLink` → `src/lib/sign-in.ts`:

1. `parseSignInEmail` (`src/lib/validation.ts`): убрать пробелы по краям, перевести в нижний регистр, не пусто, не длиннее 254, шаблон адреса. Ошибка → «Проверьте адрес почты». Тест проверяет, что адреса, которые принимает наше правило, принимает и Better Auth
2. Транзакция с `pg_advisory_xact_lock` по почте: два одновременных запроса одной почты идут по очереди
3. Удалить записи `sign_in_emails` старше 10 минут; если для почты уже 3 записи → «Слишком часто, попробуйте через несколько минут»
4. Удалить прежние ссылки этой почты из `verifications` (`identifier` начинается с `magic-link:`, в JSON `value` - эта почта)
5. `auth.api.signInMagicLink` с `callbackURL: "/"` и `errorCallbackURL: "/login/expired"` - Better Auth создаёт ссылку и вызывает отправку письма
6. Записать отправку в `sign_in_emails`, завершить транзакцию

Если письмо не ушло, шаг 5 бросает ошибку, транзакция откатывается: попытка не идёт в лимит, старые ссылки остаются рабочими. Новая ссылка остаётся в базе, но её никто не получил, и через 15 минут она истекает. Пользователь видит «Не удалось отправить письмо. Попробуйте ещё раз через минуту».

Транзакция держит одно соединение на время отправки письма (секунды) - для приложения на несколько человек это не важно.

Шаг 4 опирается на внутренний формат записи Better Auth. Тест «две ссылки подряд» упадёт, если формат поменяется при обновлении.

Альтернативы: встроенный лимит Better Auth считает по IP, а не по почте; гасить старые ссылки внутри `sendMagicLink` без блокировки - два одновременных запроса могут погасить друг друга.

### 4. Письма

- `src/lib/mailer.ts` (`server-only`): Nodemailer по SMTP, настройки из `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`. Локально и в тестах - Mailpit (порт 1025, без пароля), на сервере - SMTP Resend (`smtp.resend.com`, 465, пользователь `resend`, пароль - ключ API)
- Текст письма - чистая функция `buildSignInEmail(url)` (HTML и простой текст), её проверяет Vitest
- В лог при сбое - только код ошибки, без адреса: тексты ошибок SMTP часто цитируют получателя

Альтернатива: HTTP API Resend - другая библиотека и разный код для заглушки и сервера, а спека требует один Nodemailer.

### 5. Проверка входа и доступ к данным

- `src/lib/session.ts` (`server-only`): `getCurrentUser()` через `auth.api.getSession` (обёрнут в `cache` React, один запрос к базе на страницу) и `requireUser()` - нет входа → `redirect("/login")`
- Все функции `src/lib/contacts.ts` и `src/lib/groups.ts` получают `ownerId` первым аргументом:
  - чтение - `where owner_id = ownerId`; заметки, «последнее общение» и метки - через контакт владельца
  - изменение и удаление - `where id = … and owner_id = …`; чужая запись = «не найдена»
  - связь «контакт - группа» и группы нового контакта - `insert … select` только из контакта и групп этого владельца; ни одной строки → «не найдено» или группа пропущена
- Каждое серверное действие и каждая страница с данными сначала вызывают `requireUser()` и передают `user.id` дальше
- `src/proxy.ts`: быстрая проверка без базы. Нет cookie входа (`getSessionCookie`) → `/login`. Пропускает `/login`, `/api/auth/*`, `/health` и статику. Это не защита, а быстрый переход: защита - пункты выше
- Страница входа и «Ссылка устарела» - `src/app/login/page.tsx` и `src/app/login/expired/page.tsx`. Вошедшего страница входа отправляет на главную
- Шапка (`layout.tsx`): почта и «Выйти» - в `Suspense`, только при входе. «Выйти» - серверное действие: `auth.api.signOut` удаляет только эту сессию, затем `/login`

Альтернатива: проверять вход только в proxy - одна ошибка или уязвимость в proxy открыла бы все данные.

### 6. Продление входа

Better Auth сдвигает срок сессии и cookie, когда сессию читают через свой маршрут или из серверного действия. При отрисовке страницы (RSC) cookie ставить нельзя, и `nextCookies` продление пропускает. Поэтому маленький клиентский компонент в шапке при загрузке страницы делает один запрос `GET /api/auth/get-session`. Если с прошлого продления прошло больше часа, срок становится «30 дней от сейчас».

Альтернатива: продлевать в proxy - запрос к базе на каждый переход и каждую предзагрузку ссылок, документация Next.js против.

### 7. Миграция и почта владельца

- Две миграции, обе генерирует `drizzle-kit generate`:
  - `drizzle/0003_auth.sql` - только новые таблицы Better Auth и `sign_in_emails`, существующие данные не трогает
  - `drizzle/0004_owners.sql` - перенос данных, дописываем руками: (1) `owner_id` пока без `not null`; (2) блок `DO`: если в `contacts` или `groups` есть строки - почта из `current_setting('app.owner_email', true)`; пусто → `raise exception` с текстом «OWNER_EMAIL is not set»; иначе найти или создать пользователя с этой почтой (пробелы убраны, нижний регистр) и проставить его `owner_id` всем контактам и группам; (3) `owner_id` → `not null`, внешние ключи, новый уникальный индекс групп вместо старого
- Отдельный файл для переноса данных - его проще показать владельцу до merge
- Все ожидающие миграции идут в одной транзакции мигратора: упало - база как была, новая версия не стартует (так уже устроен `deploy.sh`)
- Почту передаёт `scripts/migrate.mts`: перед миграциями на том же соединении `set_config('app.owner_email', OWNER_EMAIL)`. Скрипт начинает читать `.env` через `@next/env`, как скрипт демо-данных, а `pnpm db:migrate` переходит на него с `drizzle-kit migrate`: drizzle-kit не умеет передать почту
- Тест миграции (Vitest): отдельная база `<имя>_migration_test`, на неё накатываются миграции до 0003, вставляются контакты, заметки, группы и связи, затем 0004 - с почтой и без. Проверяем: числа строк равны, всё у владельца; без почты - ошибка и данные не тронуты; на пустой базе почта не нужна
- Скрипт демо-данных: находит или создаёт пользователя `OWNER_EMAIL`, вставляет контакты с его `owner_id`; если у него уже есть контакты - ничего не делает

Альтернатива: почта в коде миграции - владелец выбрал `.env`, чтобы почты не было в git и в образе.

### 8. Mailpit и тесты

- `compose.yaml`: сервис `mailpit` (образ `axllent/mailpit`, последняя стабильная версия), SMTP `127.0.0.1:1025`, страница `127.0.0.1:8025`
- CI: Mailpit - сервис в заданиях `unit` и `e2e`
- Playwright: `BETTER_AUTH_URL=http://127.0.0.1:3100`, SMTP - Mailpit, `BETTER_AUTH_SECRET` - случайный при каждом запуске (не хранится в git)
- Тесты находят письма в Mailpit по адресу получателя, уникальному для теста: `pnpm test` и `pnpm test:e2e` могут идти одновременно
- Сбой отправки в Vitest: адрес SMTP на время теста указывает на порт, где никто не слушает (`vi.stubEnv`) - настоящая ошибка соединения, без моков
- Время в e2e не ждём, а сдвигаем в базе, как в тестах «Пора связаться»: срок ссылки (`verifications.expires_at`), срок и время продления сессии (`sessions`)
- e2e главного сценария и «Пора связаться»: пользователь и его контакты создаются в базе, затем тест входит через страницу входа и письмо. «Другой браузер» входит под той же почтой
- Новый `e2e/login.spec.ts`: критерий успеха про A и B и сценарии входа, которые требуют браузера. Что покрыто чем - в tasks.md

### 9. Настройки и выкатка

- Новые строки `.env`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_*`, `MAIL_FROM`, `OWNER_EMAIL`. В `.env.example` и `deploy/.env.example` - без значений. Агенту чтение `.env*` запрещено настройками проекта: строки дописываются в конец файла, а владелец сверяет
- `deploy/compose.yaml`: приложению - настройки входа и почты через `${VAR:?…}`: нет строки - выкатка останавливается ещё до бэкапа. Контейнерам `migrate` и `seed` - `OWNER_EMAIL`
- Образ собирается без настоящих ключей: если сборка требует `BETTER_AUTH_SECRET`, в `Dockerfile` - заглушка, как для `DATABASE_URL`
- nginx не меняется

## Risks / Trade-offs

- [Почтовый сканер (антиспам в рабочей почте) открывает ссылку раньше человека и гасит её] → человек видит «Ссылка устарела». Сейчас не лечим: спека требует вход в один клик. Если случится - отдельное решение владельца (например, страница с кнопкой «Войти»)
- [После выкатки почта на сервере не работает - не войдёт никто, даже владелец] → домен в Resend и строки `.env` готовы до merge; сразу после выкатки владелец входит на проде. Откат - раздел ниже
- [Письма попадают в спам] → домен отправки подтверждён в Resend записями SPF и DKIM
- [Гашение старых ссылок зависит от внутреннего формата записи Better Auth] → тест «две ссылки подряд» ловит изменение при обновлении
- [Обновление Better Auth меняет таблицы] → при обновлении снова прогоняем `auth generate` и сравниваем со схемой
- [Без JavaScript вход не продлевается] → держится 30 дней с последнего продления; приложение без JavaScript и так почти не работает
- [В сессии Better Auth хранит IP и браузер] → нигде не показываются, удаляются вместе с сессией
- [Next.js 16.4.0 с известной уязвимостью] → защита данных не зависит от proxy (раздел 5), но обновление до выкатки входа - вопрос владельцу в proposal.md

## Migration Plan

До merge:

1. Владелец: домен отправки в Resend, записи DNS, ключ API
2. Владелец: строки в `.env` на сервере (права 600) и локально, включая `OWNER_EMAIL`; секрет - командой, которую скажет агент
3. Агент показывает владельцу `drizzle/0004_owners.sql` и прогон на локальной базе с демо-данными: число контактов, заметок и групп до и после

Выкатка - обычная: бэкап → миграция (данные переходят владельцу) → новая версия → `/health`. Затем владелец входит на проде и сверяет числа, потом входит второй человек.

Откат - только вместе, и образ, и база: старая версия без входа на новой базе показала бы любому посетителю все контакты. Поэтому для этой выкатки порядок обратный общему из README: сначала `restore.sh` с бэкапом, снятым этой выкаткой (новая версия на старой базе не откроется, но и данных не покажет), затем `deploy.sh` с прошлым SHA. Запускает владелец; в README - отдельная заметка про этот порядок.
