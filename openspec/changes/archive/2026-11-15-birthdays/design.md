# Design

## Context

Требования - в `specs/contact-birthdays/spec.md`, мотивация - в `proposal.md`. Что уже есть и на что опираемся:

- Блок «Пора связаться» (`src/components/overdue-contacts.tsx`, `listOverdueContacts` в `src/lib/contacts.ts`): дни считает Postgres, часовой пояс - константа `Europe/Moscow`, функции принимают необязательный `now` для тестов
- Поле «Как часто общаться» в карточке сохраняется сразу через серверное действие (`setContactFrequency`), ошибка показывается под полем, при сбое значение откатывается (`useOptimistic`)
- Форма нового контакта (`src/components/contact-form.tsx`) собирается из списка полей `FIELDS`; проверка - `parseContactForm` в `src/lib/validation.ts`, она же на сервере
- `src/db/schema.ts` не импортирует ничего из `src/` (его копирует образ для seed-скрипта)
- Все запросы фильтруются по `ownerId`

## Goals / Non-Goals

**Goals:**

- Дата рождения живёт в базе, проверяется на сервере и не может быть «наполовину» заполненной
- «Скоро» считает база одним запросом, по тем же правилам Москвы, что и «Пора связаться»

**Non-Goals:**

- Общий механизм правки полей карточки: поле даты - единственное новое редактируемое поле
- Новые библиотеки (работа с датами, маски ввода)

## Decisions

### 1. Модель данных: три поля в `contacts`

- `birthday_day` - `smallint`, может быть пустым
- `birthday_month` - `smallint`, может быть пустым
- `birthday_year` - `smallint`, может быть пустым

CHECK-ограничения в базе (последняя линия обороны, остальное проверяет приложение):

- день и месяц либо оба пустые, либо оба заданы
- месяц от 1 до 12; день от 1 до 31 и не больше числа дней в месяце, при этом для февраля допускается 29
- год задан только вместе с днём и месяцем

Проверка «год не в будущем» и «29 февраля только в високосный год» - в приложении: база не знает «сегодня по Москве» в CHECK, и ограничение со временем ломается при восстановлении бэкапа.

Альтернативы:

- Один `date` с условным годом для «года нет» (например, 1904) - подставной год легко принять за настоящий, а «исполняется N» пришлось бы отдельно отличать
- Один `date` + флаг «год известен» - 29 февраля в невисокосном году не сохранить, а для даты без года он нужен
- Текст `ДД.ММ[.ГГГГ]` - нельзя считать «ближайшие дни» запросом

### 2. Разбор и показ даты - чистый модуль `src/lib/birthday.ts`

Без `server-only` и без базы, чтобы его тестировали быстро и использовал и сервер, и форма.

- `parseBirthday(text, currentYear)` → `{ day, month, year | null }`, `null` для пустого текста или ошибка с сообщением из спеки. Принимает `Д.М`, `ДД.ММ`, `ДД.ММ.ГГГГ`, пробелы по краям убирает; года из 1–3 цифр - ошибка формата
- `formatBirthday({ day, month, year })` → `05.03` / `05.03.1990` - значение в поле
- `formatBirthdayDate(day, month)` → «18 ноября» для строки блока (`Intl.DateTimeFormat("ru-RU", { day, month: "long", timeZone: "UTC" })`)
- Текущий год - по Москве; его считает вызывающий код сервера и передаёт в `parseBirthday`, чтобы тесты задавали год сами

В `src/lib/validation.ts` форма нового контакта получает поле `birthday` рядом с остальными: `parseContactForm` вызывает `parseBirthday`, ошибки идут тем же путём, что у других полей, а `ContactInput` получает `birthdayDay`, `birthdayMonth`, `birthdayYear`.

### 3. «Скоро» считает Postgres одним запросом

Функция `listUpcomingBirthdays(ownerId, now?)` в `src/lib/contacts.ts`, по образцу `listOverdueContacts`:

- «сегодня» - `todayAt(now)`, уже существующий фрагмент (дата по Москве от часов базы)
- день рождения в году Y: первое число месяца + (день − 1), но не позже последнего дня месяца. Так 29 февраля в невисокосный год даёт 28 февраля, как и конец месяца в «Пора связаться»
- ближайший: в этом году, если он не раньше сегодня, иначе в следующем. Это же решает переход через конец года
- дней до него = ближайший − сегодня; в выдачу только от 0 до 6
- «исполняется» = год ближайшего дня рождения − год рождения; в выдачу, только если год задан и результат не меньше 1
- порядок: дней до дня рождения по возрастанию, затем имя с русской сортировкой (как в списке), затем `id`
- возвращает `id`, `name`, день, месяц, дней до, сколько исполняется

Только `ownerId` текущего пользователя; запрос не принимает поиск и группу.

Альтернатива - считать в JS: пришлось бы тянуть всех контактов с датами на страницу и держать часовой пояс и 29 февраля в двух местах (SQL «Пора связаться» и JS). Для личной CRM разницы в скорости нет; выбираем единый стиль - всё про «сегодня» считает база.

### 4. Серверные действия

- `createContact` (уже есть): читает поле `birthday` формы, проверяет вместе с остальными, при ошибке возвращает `errors.birthday` и введённые значения. Группы и остальные поля не теряются, как сейчас
- Новое `setContactBirthday(contactId, value)` по образцу `setContactFrequency`: проверяет `contactId`, значение (любое, кроме строки, считается пустым - данные идут от клиента), разбирает дату, обновляет контакт владельца, `revalidatePath("/")` и `refresh()`. Возвращает `{ error }`: «Контакт не найден» для чужого и несуществующего, сообщение разбора для неверной даты. Успех - `{ value }` с нормализованной датой (`05.03`), чтобы поле сразу показало сохранённый вид
- Функция `updateContactBirthday(ownerId, contactId, birthday | null, ...)` в `src/lib/contacts.ts`: один `UPDATE ... WHERE id AND owner_id`, возвращает, нашёлся ли контакт

### 5. Поле в форме и в карточке

- Форма: в `FIELDS` добавляется «День рождения» после «Почта»: обычное текстовое поле (не `inputMode="numeric"`: на цифровой клавиатуре телефона нет точки, а дата вводится с точками), `maxLength` 10, подсказка «Например: 14.03 или 14.03.1990». Ошибка и фокус на поле при неверной дате - тем же кодом, что у остальных полей
- Карточка: новый клиентский компонент строки «День рождения» (после «Почта», перед «Группы»). Поле ввода, не «текст + кнопка», чтобы не добавлять режимы чтения и правки. Сохраняется при потере фокуса и по Enter, только если текст изменился. На время запроса поле доступно, повторная отправка того же значения не уходит. Неверная дата - сообщение под полем, текст остаётся. Сбой связи - сообщение и возврат к сохранённому значению (как у частоты). Успех - в поле нормализованный вид
- Подпись связана с полем (`label`), сообщение - через `aria-describedby`; на телефоне размер текста 16 px, чтобы браузер не приближал страницу при фокусе

Альтернатива - три выпадающих списка (день, месяц, год): сохранять при смене каждого нельзя, пока дата неполная, а список из 125 годов неудобен на телефоне.

### 6. Блок на главной

- Данные - в компоненте `Contacts` в `src/app/page.tsx`, параллельно со списком и просрочкой (`Promise.all`), под той же заглушкой загрузки
- Новый компонент `UpcomingBirthdays` (серверный, без состояния: в строках нет кнопок). Стоит под `OverdueContacts`, над поиском; пустой список - `null`
- Стиль - дизайн-токены, отличный от тёмно-синей панели «Пора связаться» (светлая панель-карточка), чтобы блоки не сливались. Конкретные токены выберет реализация по `globals.css`; нового цвета не вводим
- Строка - одна ссылка на карточку (кнопок нет, значит вложенных интерактивных элементов нет): аватар, имя, дата и «исполняется N»; справа «сегодня» / «завтра» / «через N дней» (`pluralize`). На телефоне «через N дней» под датой. Высота строки не меньше 44 px
- `revalidatePath("/")` уже вызывают `setContactBirthday` и `deleteContact`, поэтому блок обновляется при возврате на главную

### 7. Тесты

- Vitest без базы: `parseBirthday`, `formatBirthday`, `formatBirthdayDate`
- Vitest на настоящей базе `_test` (по образцу `contacts.test.ts`): `listUpcomingBirthdays` с фиксированным `now` (окно, переход через год, 29 февраля, Москва, порядок, чужие контакты), `updateContactBirthday`, `insertContact` с датой, CHECK-ограничения
- Playwright (`e2e/birthdays.spec.ts`): экраны. Сервер считает «сегодня» по своим часам, поэтому даты в тесте - от сегодняшнего дня по Москве (сегодня, +6, +7, вчера), а не фиксированные

## Risks / Trade-offs

- [Текст `ДД.ММ` непривычен тем, кто ждёт календарь] → в форме подсказка с примером; при неверной дате - понятное сообщение. Календарь с выбором - отдельное решение, если станет мешать
- [Дата, сохранённая по уходу из поля, может уйти случайно: человек кликнул мимо] → отправляется только изменённое значение, а неверное не затирает старое
- [29 февраля: два разных результата в високосный и обычный год] → правило записано в спеке и покрыто тестами с фиксированными датами
- [Блоки «Пора связаться» и «Скоро день рождения» вместе занимают много места над поиском] → принимаем; блок дней рождения показывается только в неделю праздника
- [Возраст «исполняется N» считается по году ближайшего дня рождения, а не по сегодняшней дате] → так и нужно: в строке будущее событие

## Migration Plan

1. `pnpm db:generate --name birthdays` создаёт `drizzle/0005_birthdays.sql`: три `ALTER TABLE contacts ADD COLUMN` без значения по умолчанию и CHECK. Существующие строки получают пустые значения; данные не меняются, поэтому по правилам проекта показывать миграцию до merge не нужно, но в PR она будет видна
2. Выкатка обычная: merge → образ → тест-стенд (миграции → образ → smoke) → прод
3. Откат: старая версия приложения с новой базой работает, так как поля необязательные. Откат версии прода через Deploy prod; поля в базе остаются и не мешают
